# 测试影响分析

读取目标仓库的本地说明及相关规格、平台规则。先固定分析对象和版本，按用户指定的仓库、提交或分支读取证据。对同名功能或不明确的对比口径，先利用仓库上下文缩小歧义，再确认会改变范围的差异。

- **提交或分支**：在分析时核对实际基线和候选 SHA。单提交通常比较父提交到该提交，合并提交确认所需父线。分支改动通常比较 merge-base 到候选，用户指定端点比较时沿用该口径。读取真实差异及必要上下文。默认使用所选提交树，工作区改动仅在明确纳入时分析。遇到子模块或依赖版本变化，按两端锁定版本查差异；对象缺失时记录未知。提交标题和文档变更只能作为线索。
- **功能或需求**：从规格或名称定位可见入口、角色、主链路和状态，再核对调用方、配置、原生宿主、共享组件、接口及现有测试。区分规格期望、候选版本实现和运行证据；按候选树锁定的子模块或依赖版本核对实际代码和入口，文档所述实现依赖未核实时标明。
- 由变更或需求沿调用关系追踪直接影响和必要回归。按实际调用和构建覆盖判断平台。按需检查权限、异常恢复、存量兼容、配置回退和非功能行为。依据不足的预期或端归属写入待确认项。纯文档且已核实没有行为差异时，可给出空的运行回归范围及理由。

## Markdown 交付格式

保存独立 Markdown。用户未指定文件名时选用可辨识且不覆盖已有产物的名称。优先采用用户指定的章节和模板。用户给出格式参考时，借鉴标题层级、用例字段和颗粒度，按本轮证据重新确定环境、账号、测试数据、适用端和预期。

默认按以下顺序组织章节。

- **修改文件** — 按模块列出与测试范围直接相关的已修改文件，用普通文本 `[文件名.扩展名 功能]`，例如 `[KingkongView.kt 工作台 H5 跳转]`。同名文件按所属模块区分。按需求或规格分析且没有可核实的修改文件时，省略本节。
- **影响范围** — 简列受影响的页面、功能和端，区分直接影响和必要回归。只写会改变测试覆盖的范围边界。
- **基本配置** — 有共用执行配置时，列出已核实且影响执行的环境、测试端、入口或测试版本。浏览器、视口、登录方式、适配器等按场景需要填写。
- **全局前置与测试数据** — 有共用前置时，集中列出账号角色、权限、开关、所需初始数据和素材。各用例只补该场景特有的条件。
- **测试范围** — 按业务模块组织，用编号标题和下列字段列出用例。已核实无运行回归时，在本节说明理由即可。

### 测试范围的用例写法

按「三级标题写业务模块 → 四级标题写 `TC-01 页面或功能 — 可验证行为`」组织。编号在文档内唯一，修订已有范围时沿用同一场景的编号。以能独立执行和判定的场景为单位，按产品风险与团队口径标优先级，例如 P0、P1。

每条用例按以下顺序填写字段。

- **优先级**、**适用端**、**类型**。类型写「只读」或「写操作」，按步骤是否会改变业务状态判断。保存、发送、删除等写操作标明测试对象、实际提交点，以及需要时的数据还原方式。确认要求以本轮已明确的执行规则为准。
- **前置条件**。写明可找到的页面入口、角色、初始状态和该用例需要的数据。优先用页面名及用户操作路径，必要时补充已核实的路由或页面标识。入口、权限、步骤或预期因平台而异并影响执行时拆分用例，一致时合并并列出适用端。
- **操作步骤**。编号写出实际点击、输入、切换或提交的顺序，能从前置条件开始执行。
- **预期结果**。与关键步骤对应，写清可观察的页面跳转、文字、显隐、列表变化或保存回显等。用具体结果判断通过，例如「返回列表后，该商品的标题显示为保存时输入的值」。
- **截图留证**。场景需要截图或用户要求留证时，标出截图时机及与编号对应的名称。用户要求接入自动化时，按目标工具的约定补充断言标签和运行配置。

只有会影响执行或预期的缺口才列待确认，并注明受影响的测试编号。分支、SHA、提交记录、对比表、构建分析记录和源码完整路径留在分析依据中。用户明确要求审计、对比详情或源码位置时，按请求单独提供对应信息。交付前确认文件标签均为纯文本，检查用例覆盖、入口可达性，以及操作和预期是否可逐项核对。

独立调用交付 Markdown。由入口串联时，传回实际写出的文件路径，并说明是否满足直接继续生成用例的条件及理由。
